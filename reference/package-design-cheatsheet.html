Package Design Cheatsheet

Shipping the procedural-animation toolkit as a reusable package. Taught in Lesson 8; grounded in Ousterhout, A Philosophy of Software Design.

The one principle

An entity IS a creature by its components. No God-component, no class hierarchy. Small, focused, independently useful components; the creature is their sum. Composition is the API.

Deep modules

  • Deep = simple interface over powerful implementation. "The cost of a module is its interface."
  • Gait = 4 floats hiding a state machine + partner guard. Aim for that ratio everywhere.
  • Split/join modules for the deepest interface, fewest dependencies, best information hiding.

Three moves that keep it deep

MoveShape
Config baked, state separateAuthoring MonoBehaviour → Baker → immutable Config (IComponentData/blob). Mutable runtime state in separate components. Data ≠ behaviour.
Two layers + escape hatchPure static Burst primitives (Ik.Solve2Bone, Fabrik.Solve, SecondOrder.Step) AND authoring components. Deep facade for 90%; primitives for off-road.
Glossary = vocabularyField names from the domain (RestLength, BendSign, GrabStrength, Comfort). Ubiquitous language = discoverability. Keep glossary and API in sync.

Progressive disclosure

  • Sensible defaults: AddComponent<Gait>() already walks.
  • Advanced knobs available, never required.
  • Component set + field names = the contract. Implementation (solver, jobs, LOD, SIMD) free to change forever.

Ship checklist

  • ☐ Every component deep (few knobs, much power)?
  • ☐ Config baked immutable; runtime state separate?
  • ☐ Primitives exposed as static Burst functions (escape hatch)?
  • ☐ Field names match the glossary?
  • ☐ Defaults make the common case zero-config?
  • ☐ Can you swap an implementation without breaking a consumer?
