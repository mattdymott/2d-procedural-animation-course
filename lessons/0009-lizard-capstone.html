2D Procedural Animation with Unity DOTS — Lesson 9

Capstone: The Creature Tick

You have all the ingredients. The capstone is not a ninth solver; it is the thing that turns a package full of good solvers into one creature. A lizard feels coherent when each subsystem makes exactly one kind of claim, in the right order.

The one rule: later stages strengthen reality, not rewrite intent

Gameplay has an intent: go that way. Muscles make a wish: curve and undulate. Gait makes a promise: this foot stays here. IK turns that promise into a leg pose. Constraints declare the final legality. Only after that may presentation add a lie for the eye — follow-through, lean, squash. That lie must never move a physics point.

The capstone seam preserves the deep modules from Lesson 8: gait owns targets, IK owns joint geometry, verlet owns the spine, and presentation owns only pixels. When a creature is wrong, trace a hand-off before turning a knob.

The creature tick

Recipe · fixed-step authority flow 
1. intent        = gameplay / steering chooses desired root motion
2. body wishes   = verlet integrates; muscles propose rhythm + tone
3. gait promises = planted/swinging state writes each foot target
4. IK            = solve knees and ankles from those foot targets
5. hard resolve  = relax spine constraints and enforce pins
6. presentation  = read resolved pose; add optional second-order juice

Gait writes targets; IK reads them. Muscles propose positions; constraints dispose of them. A visual filter reads the answer; it cannot be allowed to move a physics point. Those arrows prevent the classic capstone failure: a lovely isolated demo that jitters, slides, or explodes once composed.

Mapping it to DOTS

DOTS mapping — a composed lizard, not a God-component

Keep your L8 surface. One entity owns its spine and leg buffers; immutable tuning stays baked config. Systems are ordered only because one produces the next system’s input.

// baked config: data designers tune once
public struct LizardConfig : IComponentData
{ public float SpineRest, MuscleStrength, Comfort, StepLead, StepDuration; }

// mutable, per-creature state
[InternalBufferCapacity(8)] public struct SpinePoint : IBufferElementData
{ public float2 P, Prev; }
public struct GaitLeg : IBufferElementData { /* plant, target, phase */ }
public struct Limb2Bone : IBufferElementData { /* hip, knee, ankle */ }
public struct PresentationFollow : IComponentData { /* L6 Y, Yd, Xp */ }

// FixedStepSimulationSystemGroup data hand-off:
// IntentSystem → BodyWishSystem → GaitSystem → TwoBoneIkSystem
//              → ConstraintResolveSystem → PresentationSystem

A typical spine buffer fits inline when its capacity matches the creature’s usual point count; Unity documents that a dynamic buffer which outgrows its internal capacity moves outside the chunk and stays there. That makes this small, fixed body a natural [InternalBufferCapacity] case. Unity’s current buffer-capacity guidance is the final word for a real package.

Build it in Unity: one honest vertical slice

  1. Start with one lizard prefab: an 8-point spine and two legs. Draw points, links, hip roots, and foot targets.
  2. Make it stand still first: pins legal, IK targets reachable, stretch error quiet.
  3. Add intent and gait. Record one visible invariant: a planted foot’s world target does not move.
  4. Add the body wave at partial strength. If it fights the feet, inspect authority and order before changing strength.
  5. Finally add presentation follow. Toggle it off: simulation must still walk; only character should disappear.
