Capstone: The Top-Down Creature Tick

The pivot is now complete. A creature can choose legal planar footholds, turn while preserving a base, and make each swing visible. This lesson puts those rules in one order that keeps their owners clear.

The top-down hand-off

Lesson 9 supplied the course’s general authority flow. A top-down creature does not replace it—it specializes the gait stage with heading-relative homes, planar candidates, a support policy, and render-only lift.

Recipe · one fixed top-down tick
1. Intent             = gameplay writes desired planar velocity
2. Planar locomotion  = move body, resolve body obstacles, update heading + homes
3. Candidate adapter  = publish walkable/path-clear candidates as world facts
4. Gait               = choose eligible leg; commit one planar SwingTo or hold Plant
5. IK + hard resolve  = pose limb, preserve links/pins, enforce final legality
6. Presentation       = derive lift, shadow, sort, and optional second-order juice

The important edge is between stages 3 and 4: the query reports evidence, but only gait is allowed to turn it into a new foot promise. The next edge is between stages 5 and 6: presentation reads a resolved planar pose and never repairs it.

Place each state with its owner

Select every state the gait stage is allowed to write. This is the narrowest useful debugging question: when a foot slides, find the writer that crossed this boundary.

The gait stage is a compact policy engine

InputDecisionOutput
Body pose, heading, velocityRotate local homes and measure plant stress.Step urgency.
Planted-foot setReject any lift that loses authored support.Eligible legs.
Planar world factsFilter walkable, path-clear, reachable candidates.One legal SwingTo.
Swing progressCommit landing when complete.New Plant.

Those inputs are intentionally small. Gait has no reason to know whether a tile map, physics scene, or distance field produced the candidates; it does not pose a knee; and it cannot see the lifted sprite. Its interface stays deep because it owns exactly the decision it needs to make.

DOTS mapping

Keep the systems ordered by the data each produces, not by a vague “animation” group. The candidate adapter runs before the fixed solve group; its compact buffer is the only world-query dependency that gait reads. Presentation can run after the fixed group and use a separate render-facing component or bridge.

// Consumer-facing solve order:
PlanarLocomotionSystem
  → PlanarCandidateAdapterSystem
  → TopDownGaitSystem
  → TwoBoneIkSystem
  → ConstraintResolveSystem
  → FootPresentationSystem

// Gait reads body pose + candidate facts and writes only:
// GaitLeg.State, GaitLeg.Plant, GaitLeg.SwingTo, GaitLeg.SwingT

Build it as one honest vertical slice

  1. Draw the planar body position, heading, local homes, and current plants.
  2. Make a stationary 90° turn. One support-eligible leg should swing; no plant should slide.
  3. Add one blocked island. Candidate data should change only when a new swing begins.
  4. Render shadow and lift from the committed target. Disable presentation: the simulation should still be legal.
  5. Only then add moving supports, special gait phases, or second-order body language.

Check yourself

Retrieve the hand-off from world evidence to a visible foot, without giving two systems the same decision.
