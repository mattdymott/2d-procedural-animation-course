Top-Down Foot Readability: Lift Is a Picture

A foot swinging across a top-down plane can be mechanically perfect and visually invisible. Give it lift, a shadow, and deliberate draw order—but leave the gait promise exactly where it was.

One planar truth; two visual cues

Gait and IK produce one authoritative point on the movement plane. Presentation derives two visible things from it: a shadow at that point and a foot sprite offset upward on screen during swing. Neither is a new world-space target.

Recipe · decorate a committed planar trajectory
// Simulation: gait/IK own this point.
float2 planarFoot = leg.State == Planted ? leg.Plant : leg.SwingTarget;

// Presentation: derive a readable picture.
float lift = visual.StepHeight * 4f * swingT * (1f - swingT);
float2 shadowScreen = Project(planarFoot);
float2 footScreen   = shadowScreen + screenUp * lift;

DrawShadow(shadowScreen);
DrawFoot(footScreen, SortFromGroundPoint(planarFoot) + visual.SwingBias);

// Never write footScreen or lift back into Plant, SwingTarget, IK, or collision.

The familiar parabola is now a visual height curve, not a side-view ground equation. It begins and ends at zero, which lets a foot lift off and land on its committed planar point without a snap.

The playground: separate the foot from its shadow

Set the swing near halfway. The pale shadow stays on the planar target; the gold foot rises in screen space. At either endpoint the two meet again. The target itself never moves because of this display choice.

Sort semantics, not accidental screen coordinates

ThingDerived fromReason
Shadow placementPlanar foot pointShows the true contact relationship.
Foot screen offsetVisual lift curveMakes swing state readable.
Base sort keyPlanar foot pointStays stable through the arc.
Foliage/wall ruleExplicit presentation policyArt direction, not simulation.

If the renderer automatically sorts from a sprite’s raised screen Y, a foot can appear to pass behind the wrong object halfway through its arc. Give the presentation adapter the planar base key plus an explicit swing bias instead. That makes occlusion a chosen game rule.

DOTS mapping

Keep runtime foot state in the gait buffer and solver output. A presentation system reads those values and emits a render-facing offset, shadow data, and sort key. The simulation systems remain independent of sprite orientation, screen-up direction, and draw ordering.

public struct FootPresentation
{
    public float2 ShadowPoint;  // projected PlanarFoot
    public float VisualLift;    // derived from SwingT
    public int SortKey;         // derived from PlanarFoot + authored policy
}

// Presentation writes this transient view data; gait never reads it.

Where to go deeper

Primary source: Joar Jakobsson and James Therrien’s Rain World Animation Process describes the foundational separation in this course: simulated points and constraints first, then graphics draped over their result. Use that mindset whenever a visual cue seems tempted to become simulation authority.

Keep the top-down foot readability cheatsheet beside top-down locomotion, support policy, and second-order dynamics.

Suggested real-world rep: render a shadow decal from each L9 planar foot target, then offset only a swinging foot sprite along screen-up. Freeze the gait state and scrub swing progress from 0 to 1: the shadow must stay at the committed target, while only the visual foot rises and falls.

Ask about sort keys for isometric art, shadows in URP 2D, or adding squash and anticipation without giving presentation authority over gait.
