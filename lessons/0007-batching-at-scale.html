2D Procedural Animation with Unity DOTS — Lesson 7

Batching at Scale: Spending the Frame Budget

Six lessons asked "does it look alive?" This one asks "does it fit the frame?" You already know DOTS — jobs, Burst, chunks. So this isn't about ECS mechanics; it's about the handful of patterns that decide whether your creatures run 200 or 50,000 at a time. The physics is cheap per creature. The scale comes from spending the budget where it's seen.

The cost lens

A creature from Lessons 1–6 — a verlet chain, two IK legs, a few second-order filters — is a rounding error on its own: sub-microsecond. But you have thousands, and 60fps gives you 16.6ms total to share with rendering, gameplay, and everything else. So think in a budget: per-creature cost × count ≤ your slice of the frame. Every pattern below either shrinks the per-creature cost or shrinks the count you pay full price for.

Five patterns for animation workloads

These are the non-obvious ones — the ECS basics you already have; these are what bites specifically when the workload is procedural animation.

PatternWhy it matters here
1 · Parallelize across, never within A chain is sequential — each link reads its neighbour (L1). Don't fight that. One creature = one entity = one IJobEntity iteration; the parallelism is the ten-thousand creatures, each solved start-to-finish on one thread. Embarrassingly parallel, chunk-friendly, zero contention.
2 · Keep every creature self-contained Feet pin into the creature's own buffer (L3/L4), so the hot job needs no ComponentLookup random access — the cache killer. When a creature must react to another (flocking, threat), gather what it needs into a read-only snapshot in a prior job, then run the hot job lookup-free.
3 · Structural change is the enemy Spawning, despawning, adding/removing components moves archetypes and forces sync points that stall every worker. Make "dead", "grab-active", "swinging" into enableable components: toggling them changes no archetype and needs no ECB. Pool creatures; disable, don't destroy.
4 · Keep buffers in the chunk Size [InternalBufferCapacity] to your typical chain length so points live inline in the chunk. Overflow spills the whole buffer to the heap and wastes the inline slot — a double cache penalty, per creature, forever. A 30-point chain wants a capacity of ~32, not the default.
5 · Branchless inner loops The gait state switch and IK bendSign are branches; scattered across a Burst job they block vectorization. Prefer math.select, sign multiplies, and masks so the solver stays SIMD-wide. Burst can then do four creatures' worth of float2 math per instruction.

The multiplier: simulation LOD

Patterns 1–5 shave the per-creature cost. Simulation LOD attacks the other factor — how many you pay full price for — and it's where the orders of magnitude live. A creature forty tiles away and three pixels tall does not need ten constraint sweeps at 60Hz. Split the herd:

  • Near (on screen, large): full fidelity — every sweep, every frame.
  • Far (distant, tiny): fewer iterations, and updated every Nth frame, round-robined by entity index so the cost spreads evenly across frames.

The eye can't tell. The budget very much can — a small near-band at high fidelity plus a cheap amortized far-band routinely turns a 50ms frame into a 5ms one. That's the whole game at scale, and the playground lets you feel exactly where the wall is.

The assembled pipeline

DOTS mapping — all six lessons, ordered and gated

The full creature is a fixed chain of systems, one dependency line, gated by a per-entity LOD tier. Everything runs in FixedStepSimulationSystemGroup — every lesson assumed a fixed timestep, and this is where that promise is kept. 

// One enableable tier tag flips near/far with no structural change:
public struct FarLOD : IComponentData, IEnableableComponent { }

// System order = the data-flow you built across six lessons:
//   1. SecondOrderJob   — juice filters advance          (L6)
//   2. GaitSystem       — writes IK targets              (L4)
//   3. IkSolveJob       — 2-bone analytic / FABRIK       (L3/L5)
//   4. MuscleJob        — goal/rhythm/tone + grab blend   (L2/L5)
//   5. ChainSolveJob    — verlet integrate + pin + sweeps (L1)
// Each is one IJobEntity; dependencies chain 1→5, no sync points between.

[BurstCompile]
partial struct ChainSolveJob : IJobEntity
{
    public float T;
    public int   FrameParity;   // for round-robin far updates

    void Execute(Entity e, ref DynamicBuffer<VerletPoint> pts,
                 in ChainSettings s, EnabledRefRO<FarLOD> far)
    {
        // LOD gate: far creatures run fewer sweeps, and only every Nth frame
        int iters = s.Iterations;
        if (far.ValueRO)
        {
            if ((e.Index & 3) != FrameParity) return;   // ~1/4 frames, spread by index
            iters = math.min(iters, 2);
        }
        Integrate(pts, s, T);
        for (int k = 0; k < iters; k++) Relax(pts, s);
    }
}

Note what makes this scale: no lookups (Pattern 2), the buffer is inline (Pattern 4), the LOD gate is a branch on a cheap enableable flag not a structural query (Pattern 3), and the far round-robin (e.Index & 3) amortizes the far herd across four frames so no single frame spikes. Assign the FarLOD flag in a lightweight culling system from on-screen bounds; it's the only cross-cutting decision the whole pipeline needs.
