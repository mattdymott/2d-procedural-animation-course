2D Procedural Animation with Unity DOTS — Lesson 6

Second-Order Dynamics: Juice From One Filter

Lessons 1–5 built creatures. This one builds character, and it applies to almost anything. Second-order dynamics is a tiny filter you drop between a value and its target: position, rotation, scale, a squash amount, a camera, a health bar. The thing keeps doing what it did — the filter decides how it moves there. Overshoot, follow-through, anticipation: three knobs, one update, millions of entities.

It's a filter, not a motion

You already smooth values with a lerp (y += (x − y) · rate). That's a first-order filter: it can only ease toward the target, never past it, never before it. Add one more piece of state — a velocity that carries momentum — and the output can overshoot, ring, settle, or wind up backward first. That's second order, and those behaviours are exactly the animation principles (follow-through, anticipation, secondary motion) that read as "alive." This is the system from t3ssel8r's "Giving Personality to Procedural Animations using Math."

Three knobs, all intuitive

KnobIsFeel across its range
f — frequency (Hz) How fast it reacts Low = slow, languid, heavy · High = snappy, twitchy, light
ζ — damping How it settles 0 = rings forever · <1 = bounces then settles (lively) · 1 = fastest, no overshoot · >1 = sluggish, stiff
r — response Character of the launch <0 = anticipates (winds up backward!) · 0 = eases in · 1 = immediate · >1 = eager, overshoots to lead

The delight is that these map onto words an animator already uses. "Make it heavier" → lower f. "Make it bouncier" → lower ζ. "Give it a wind-up" → negative r. You tune with your eyes, not a calculator.

The recipe

Convert the three intuitive knobs into three constants once, then run a two-line update per frame. This is the numerically stable form — it clamps one term so a fast f at a coarse timestep can't explode:

Recipe · second-order filter 
// constants — compute once when f, ζ, r change
k1 = ζ / (π·f)
k2 = 1 / (2π·f)²
k3 = r·ζ / (2π·f)

// per fixed step, T = dt, x = target this frame, y = filtered output
xd = (x - xPrev) / T          // estimate how fast the target is moving
xPrev = x
k2s = max(k2, T²/2 + T·k1/2, T·k1)          // stability clamp
y   = y + T · yd                             // move output by its velocity
yd  = yd + T · (x + k3·xd - y - k1·yd) / k2s // update that velocity

The whole personality lives in that last line. x − y is a spring pulling the output toward the target; −k1·yd is friction that decides how it settles; k3·xd is the clever bit — it feeds the target's velocity into the output's acceleration, and when k3 is negative the output lurches away before chasing. That single term is anticipation, the animator's wind-up, falling out of the math for free.

The payoff: squash from the same filter

Here's the multiplier. The filter already computes yd — the output's velocity. Feed that straight into squash-and-stretch: stretch the sprite along its velocity, squash it perpendicular, scaled by speed. One filter now gives you both a lively follow and its secondary motion, with no extra state. The playground's blob does exactly this — watch it stretch as it launches and squish as it settles.

Mapping it to DOTS

DOTS mapping

This is the friendliest scale story in the whole course: a few floats of state and a branchless update. Bake the constants once (they only change when a designer retunes), then a single Burst job filters a million values — camera rigs, floating damage numbers, turret lead, squash amounts, UI. Attach it to any float, float2, or quaternion. 

public struct SecondOrder : IComponentData
{
    public float2 Y, Yd, Xp;   // output, output velocity, previous input
    public float  K1, K2, K3;  // baked from (f, ζ, r)
}

public static void MakeConstants(float f, float z, float r,
                                 out float k1, out float k2, out float k3)
{
    float w  = 2f * math.PI * f;
    k1 = z / (math.PI * f);
    k2 = 1f / (w * w);
    k3 = r * z / w;
}

[BurstCompile]
partial struct SecondOrderJob : IJobEntity
{
    public float T;
    void Execute(ref SecondOrder s, in FollowTarget tgt)   // tgt.Value = the input x
    {
        float2 x  = tgt.Value;
        float2 xd = (x - s.Xp) / T;
        s.Xp = x;
        float k2s = math.max(s.K2, math.max(T*T*0.5f + T*s.K1*0.5f, T*s.K1));
        s.Y  += T * s.Yd;
        s.Yd += T * (x + s.K3 * xd - s.Y - s.K1 * s.Yd) / k2s;
        // s.Y is the juiced output; s.Yd is free squash/lean velocity
    }
}

Fixed timestep, as ever — k2s assumes a known T. The output Y drives a LocalTransform; Yd drives a squash shader param or a lean angle for free. Per-instance variation in (f, ζ, r) makes a crowd of identical prefabs move like individuals — the cheapest character you will ever buy.
