Package API Design: Shipping the Toolkit

The third head of your mission. You have six techniques; now you make them a package — something future-you drops into a new project and builds a creature in an afternoon without reopening these lessons. The techniques were the hard part intellectually. The interface is the hard part that decides whether any of it gets used again.

The one principle: an entity is a creature by its components

Resist the urge to write a Creature class with forty fields. In ECS the creature isn't a type — it's whichever components an entity happens to carry. A jellyfish is VerletChain + Muscles. A lizard adds Limb2Bone + Gait. A grabbing tail is FabrikChain + GrabTarget. Composition is the API. Each component is small, focused, and independently useful; the creature is their sum. This is the ECS gift — take it.

Deep modules, narrow interfaces

Ousterhout's A Philosophy of Software Design names the target: a deep module — a simple interface hiding a powerful implementation. "The cost of a module is its interface." Your Gait component is deep: four tuning floats (Comfort, StepDuration, StepLead, StepHeight) hide a foot state machine, a partner guard, and reachability clamping. The consumer sets four numbers; the lesson-4 machinery stays invisible. Every component you ship should feel like that — few knobs, much power.

Three design moves that keep it deep

MoveWhat it buys
Config baked, state separate Authoring MonoBehaviour → Baker → immutable runtime config (blob/IComponentData). Designers tune in the inspector; the sim reads baked values; live state (Y, Yd, foot phase) lives in separate mutable components. Data and behaviour never tangle.
Two layers, one escape hatch Ship the primitives as pure static Burst functions (Ik.Solve2Bone, Fabrik.Solve, SecondOrder.Step) and the authoring components that wire them together. High-level for the 90% case; the raw functions for anyone who needs to go off-road. Never trap the power behind the convenience.
The glossary is the vocabulary Name every field from the domain language you built across eight lessons — RestLength, BendSign, GrabStrength, Comfort. A consumer who read the glossary already knows your API. Ubiquitous language is discoverability.
Progressive disclosure — the pit of success

The common case should need almost nothing: sensible defaults so AddComponent<Gait>() already walks. Advanced knobs exist but never block the beginner. And keep the component surface the contract — you can rewrite FABRIK or vectorize the verlet solver tomorrow, and no consumer breaks, because they only ever touched the interface.

The package at a glance

DOTS mapping — the shipped shape

Two layers. The consumer touches only the top; the primitives are there when they need to escape. Config bakes once; systems run in the fixed order you assembled in Lesson 7. 

// ── Layer 1: primitives (pure, static, Burst — the escape hatch) ──
namespace ProcAnim.LowLevel {
    public static class Ik        { public static void Solve2Bone(ref Limb2Bone l) {...} }
    public static class Fabrik    { public static void Solve(Span<float2> p, float2 t, ...) {...} }
    public static class SecondOrder { public static float2 Step(ref SO s, float2 x, float T) {...} }
    public static class Verlet    { public static void Integrate(...); public static void Relax(...); }
}

// ── Layer 2: authoring → baked config (designer-facing) ──
public class GaitAuthoring : MonoBehaviour {          // inspector knobs, domain-named
    public float comfort = 40, stepDuration = 0.25f, stepLead = 0.2f, stepHeight = 20;
}
public struct GaitConfig : IComponentData {           // immutable baked config
    public float Comfort, StepDuration, StepLead, StepHeight;
}
class GaitBaker : Baker<GaitAuthoring> {
    public override void Bake(GaitAuthoring a) {
        var e = GetEntity(TransformUsageFlags.Dynamic);
        AddComponent(e, new GaitConfig {              // sensible values already in authoring
            Comfort = a.comfort, StepDuration = a.stepDuration,
            StepLead = a.stepLead, StepHeight = a.stepHeight });
        AddBuffer<GaitLeg>(e);                         // mutable runtime state, separate
    }
}

// ── The creature IS its components — compose freely ──
//   jellyfish : VerletChainConfig + MusclesConfig
//   lizard    : VerletChainConfig + Limb2BoneConfig + GaitConfig
//   tail      : FabrikChainConfig + GrabTargetConfig
//   coin      : SecondOrderConfig
// Systems (fixed order, L7) read config + state; consumer schedules nothing.

The contract is the component set and its field names. Everything below — solver choice, job structure, LOD gating, SIMD — is yours to change forever without breaking a single consumer. That is what "shipped" means: a surface small enough to trust, over an implementation free to grow.
